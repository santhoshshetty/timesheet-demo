# Implementation Plan: Project Management

**Branch**: `001-project-management` | **Date**: 2026-10-06 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/001-project-management/spec.md`

## Summary

First vertical slice of `timesheet-demo`: users create, find, view, edit, and soft-delete
projects. Each project gets a system-generated, unique, 8-digit charge code. The slice runs
React frontend → REST API (`/api/v1`) → domain/application layer → PostgreSQL.

Technical approach (details in [research.md](research.md)):

- **Contract-first API**: the OpenAPI document ([contracts/openapi.yaml](contracts/openapi.yaml))
  drives request/response validation, generated TypeScript types, and Swagger UI.
- **Domain-centric backend**: business rules live in a `Project` aggregate. Three ports
  (`ProjectRepository`, `ChargeCodeGenerator`, `Clock`) isolate PostgreSQL, randomness, and
  "today".
- **Database-guaranteed invariants**:
  - Charge-code uniqueness spans all rows, including deleted ones.
  - A partial unique index enforces case-insensitive name uniqueness among active projects.
  - `CHECK` constraints back up the domain rules.
  - Optimistic locking (`version` + `ETag`/`If-Match`) prevents lost updates.
  - An `Idempotency-Key` prevents duplicate creates.
- **Random charge codes**: generated by the backend application (8 digits, bounded retry on
  collision) and stored in PostgreSQL, where a unique constraint across all projects, including
  deleted ones, guarantees they are never reused. Codes are immutable after creation.
- **Single runtime container**: the Express backend also serves the built React app (same
  origin, no extra web server).
- **Accessible enterprise UI**: React + MUI with a neutral theme, WCAG 2.1 AA checks in unit
  tests (jest-axe) and E2E tests (axe + Playwright).
- **Development-only**: no authentication (Constitution v1.3.0 Principle III exemption) and the
  audit trail is deferred (Principle VI pre-identity audit deferral). The API
  refuses to start when `APP_ENV=production`.

## Technical Context

**Language/Version**: TypeScript 5.x (`strict`) on Node.js 22 LTS (backend, tooling); browser
target ES2022. Backend compiles to CommonJS; Jest configs are plain `jest.config.cjs` (no
`ts-node`) (R18).

**Primary Dependencies**:
- Backend: Express 5, `pg`, `node-pg-migrate`, `express-openapi-validator`,
  `swagger-ui-express`, `helmet`, `pino`/`pino-http`; dev runner `tsx`.
- Frontend: React 19, Vite, React Router, MUI.
- Shared: `openapi-typescript`.
- Justifications for every package, including dev tooling:
  [research.md](research.md#dependency-justification-constitution-principle-x).

**Storage**: PostgreSQL 16 (table `project`, see [data-model.md](data-model.md)).

**Testing**:
- Jest + ts-jest (unit)
- Jest + Testcontainers with PostgreSQL 16 (DB integration)
- Jest + Supertest (API)
- Jest + React Testing Library + jest-axe (frontend)
- Playwright + @axe-core/playwright (end-to-end, run against the Docker Compose stack)

The user asked for "Playwright for integration tests"; this is mapped to browser-level end-to-end
integration. Testcontainers and Supertest remain as required by Constitution Principle VIII; see
[research.md R13](research.md).

**Target Platform**:
- Linux containers (Docker / Docker Compose) in lower environments only (dev, test, staging).
- Latest two versions of Chrome, Edge, Firefox, and Safari.

**Project Type**: Web application. SPA frontend plus REST API backend, in an npm-workspaces
monorepo.

**Performance Goals**:
- API p95 < 300 ms for create, read, and update.
- List/search p95 < 500 ms at 10,000 projects.
- Search results visible in the UI within 2 s (SC-004).

**Constraints**:
- Development-only: never deployed to production (FR-036).
- WCAG 2.1 AA (FR-034).
- Calendar dates evaluated in a configurable business time zone (`BUSINESS_TIME_ZONE`).
- No personal data in logs.
- Request body ≤ 100 KB.

**Scale/Scope**:
- ≤ 10,000 projects (design headroom to 100,000).
- Tens of concurrent internal users.
- 4 screens, 5 API operations, plus 2 health endpoints.

No `NEEDS CLARIFICATION` items remain. All were resolved in [research.md](research.md).

**Structure Decision**: Web application split into `backend/` and `frontend/`, plus a shared
`packages/api-contract/` so both sides compile against the same OpenAPI-generated types, and a
separate `e2e/` workspace for Playwright. All four are npm workspaces under one root (R1). Backend
folders follow the Constitution's layering (Principle II); frontend code is grouped by feature.
At runtime one container (`app`) serves both the API and the built frontend from the same origin
(R16).
