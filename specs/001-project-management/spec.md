# Feature Specification: Project Management

**Feature Branch**: `001-project-management` (spec directory; no git branch was created)

**Created**: 2026-10-06

**Status**: Clarified

**Input**: User description: "Project Management — create, view/retrieve, edit, and delete projects
with Project Name, Project Manager, Start Date, End Date, Project Type (Internal/Client), Billing
Type (Billable/Non-Billable), and a system-generated, unique, 8-digit numeric Charge Code. Enterprise
business-application UI. Authentication and authorization are out of scope for this first feature."

## Clarifications

### Session 2026-10-06

- Q: Must project names be unique? → A: Unique among non-deleted projects, compared ignoring
  case; a deleted project's name may be reused.
- Q: Can deleted projects be restored or permanently purged? → A: Soft delete only; no restore and
  no purge in this feature. Deleted projects are kept indefinitely.
- Q: How is the Project Manager represented before an identity system exists? → A: Name plus a
  required work email address, which serves as the identifier for linking to a future identity
  system.
- Q: Can the Start Date be in the past? → A: No. The Start Date cannot be earlier than today.
- Q: What is the Project Name length limit? → A: 100 characters maximum.
- Q: Which fields are mandatory? → A: All project fields are mandatory, including End Date.
- Q: Are authentication and audit-trail tracking part of this feature? → A: No. Both are deferred
  to later features.
- Q: Should this feature be designated development-only (never deployed to production until
  authentication/authorization exist)? → A: Yes. It may be deployed to lower (non-production)
  environments for now, but not to production.
- Q: Should a Client Project also record which client it is for? → A: Yes. A free-text Client
  Name is required when Project Type is Client Project and is not used for Internal Projects.
- Q: When editing, can the End Date move earlier, including into the past? → A: No. An edited End
  Date MUST NOT be earlier than the End Date currently saved; End Dates can be kept or extended,
  never shortened.
- Q: Can a charge code start with zero? → A: Yes. Any 8 digits are valid (`00000000`–`99999999`),
  and leading zeros are always preserved.
- Q: Should project search also match the Project Manager's name or email, and the Client Name?
  → A: Yes. Search matches project name, charge code, Project Manager name, Project Manager
  email, and Client Name.
- Q: What is the maximum length of the Project Manager Name? → A: 100 characters.
- Q: Can a charge code ever change or be reused? → A: No. A charge code is immutable for the
  life of the project (including after deletion), unique across all projects including deleted
  ones, and never reused. It is generated by the system and stored with the project.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Create a Project (Priority: P1)

A user opens the Project Management area, chooses to create a new project, fills in the project
details (name, project manager name and work email, start date, end date, project type, billing
type, and — for Client Projects — client name), and saves. The system validates the input,
generates a unique 8-digit charge code, saves the project, and shows the new project's details
including its charge code.

**Why this priority**: No other project capability is useful without projects existing. The charge
code is the key output that downstream capabilities (e.g., future timesheets) will depend on.

**Independent Test**: Create a project with valid data and confirm that a project with the entered
details and a generated 8-digit charge code is shown afterwards.

**Acceptance Scenarios**:

1. **Given** the create-project form, **When** the user enters all required fields with valid
   values and saves, **Then** the project is saved, a success confirmation is shown, and the
   project's details are displayed with a system-generated charge code of exactly 8 numeric digits.
2. **Given** the create-project form, **When** the user views the form, **Then** there is no
   editable charge code field.
3. **Given** the create-project form, **When** the user saves with one or more required fields
   empty, **Then** the project is not saved, each missing field is identified with a specific
   message, and the values already entered are preserved.
4. **Given** the create-project form, **When** the user enters an end date earlier than the start
   date and saves, **Then** the project is not saved and a message states that the end date must be
   on or after the start date.
5. **Given** the create-project form, **When** the user enters a start date of today and an end
   date equal to the start date and saves, **Then** the project is saved.
6. **Given** existing projects, **When** a new project is created, **Then** its charge code differs
   from the charge code of every other project, including deleted projects.
7. **Given** the create-project form, **When** the user submits the same form more than once in
   quick succession (e.g., double-click), **Then** only one project is created.
8. **Given** a non-deleted project named "Apollo Migration", **When** the user creates a project
   named "apollo migration", **Then** the project is not saved and a message states that a project
   with this name already exists.
9. **Given** a deleted project named "Apollo Migration", **When** the user creates a project named
   "Apollo Migration", **Then** the project is saved with a new, different charge code.
10. **Given** the create-project form, **When** the user enters a Project Manager email that is not
    a valid email address, **Then** the project is not saved and a message identifies the invalid
    email.
11. **Given** the create-project form, **When** the user enters a start date earlier than today and
    saves, **Then** the project is not saved and a message states that the start date cannot be in
    the past.
12. **Given** the create-project form, **When** the user enters a project name longer than 100
    characters, **Then** the project is not saved and a message states the 100-character limit.
13. **Given** the create-project form with Project Type "Client Project", **When** the user leaves
    Client Name empty and saves, **Then** the project is not saved and a message states that
    Client Name is required for Client Projects.
14. **Given** the create-project form with Project Type "Internal Project", **When** the user
    saves without a Client Name, **Then** the project is saved and no Client Name is stored.

### User Story 2 - Find and View Projects (Priority: P1)

A user opens the Project Management area and sees a list of projects showing the key information
for each one. The user can search the list and open a project to see all of its details.

**Why this priority**: Users must be able to confirm that created projects exist and find a
project's charge code. Together with Story 1 this forms the minimum viable slice.

**Independent Test**: With several projects already present, open the project list, search for one
by name, charge code, Project Manager, or Client Name, open it, and confirm all of its details are
shown correctly.

**Acceptance Scenarios**:

1. **Given** existing projects, **When** the user opens the project list, **Then** each
   non-deleted project is shown with its name, charge code, project manager, start date, end date,
   project type, and billing type.
2. **Given** existing projects, **When** the user searches by all or part of a project name,
   charge code, Project Manager name, Project Manager email, or Client Name, **Then** only
   matching non-deleted projects are shown, ignoring letter case.
3. **Given** a search with no matches, **When** results are displayed, **Then** a clear "no matching
   projects" message is shown with a way to clear the search.
4. **Given** no projects exist, **When** the user opens the project list, **Then** an empty state
   explains that there are no projects yet and offers a way to create one.
5. **Given** the project list, **When** the user selects a project, **Then** a detail view shows
   all project fields, including the charge code.
6. **Given** the project data cannot be retrieved (e.g., service unavailable), **When** the user
   opens the list or a detail view, **Then** a clear error message is shown with an option to retry,
   and no internal technical details are revealed.
7. **Given** the user opens a link to a project that does not exist or has been deleted, **When**
   the page loads, **Then** a "project not found" message is shown with a way back to the list.

### User Story 3 - Edit a Project (Priority: P2)

A user opens an existing project, changes one or more of its details, and saves. The system
validates the changes with the same rules as creation and keeps the project's charge code
unchanged.

**Why this priority**: Project details (e.g., dates, manager) change over time, but this is less
critical than creating and finding projects.

**Independent Test**: Edit an existing project's name and end date, save, and confirm that the new
values are shown and the charge code is unchanged.

**Acceptance Scenarios**:

1. **Given** an existing project, **When** the user changes editable fields to valid values and
   saves, **Then** the changes are saved, a success confirmation is shown, and the updated details
   are displayed.
2. **Given** an existing project, **When** the user opens it for editing, **Then** the charge code
   is displayed as read-only and cannot be changed.
3. **Given** an existing project, **When** the user saves an edit, **Then** the charge code is
   identical to its value before the edit.
4. **Given** an edit form, **When** the user saves invalid values (e.g., an empty required field or
   an end date before the start date), **Then** the changes are not saved, field-specific messages
   are shown, and the entered values are preserved.
5. **Given** two non-deleted projects, **When** the user renames one to the other's name (ignoring
   case), **Then** the change is not saved and a message states that the name is already in use.
6. **Given** two users have the same project open for editing, **When** the first user saves and
   then the second user saves, **Then** the second save is rejected with a message that the project
   was changed by someone else, and the first user's changes are not silently overwritten.
7. **Given** an edit form with unsaved changes, **When** the user chooses to cancel or leave,
   **Then** the user is warned that unsaved changes will be lost.
8. **Given** a project whose start date has already passed, **When** the user edits other fields
   without changing the start date and saves, **Then** the changes are saved.
9. **Given** an existing project, **When** the user changes the start date to a date earlier than
   today and saves, **Then** the change is not saved and a message states that the start date
   cannot be in the past.
10. **Given** a Client Project with a Client Name, **When** the user changes Project Type to
    "Internal Project" and saves, **Then** the change is saved and the Client Name is removed.
11. **Given** an Internal Project, **When** the user changes Project Type to "Client Project"
    without entering a Client Name and saves, **Then** the change is not saved and a message
    states that Client Name is required for Client Projects.
12. **Given** a project with End Date 31 December, **When** the user changes the End Date to
    31 March of the following year and saves, **Then** the change is saved.
13. **Given** a project with a saved End Date of 31 March, **When** the user changes the End Date
    to 28 February and saves, **Then** the change is not saved and a message states that the End
    Date cannot be moved earlier than its current value.

### User Story 4 - Delete a Project (Priority: P3)

A user chooses to delete a project, confirms the action, and the project no longer appears among
active projects. The project's data and charge code are kept for historical purposes and are not
permanently erased.

**Why this priority**: Deletion is needed to remove projects created in error or no longer needed,
but it is used less often than the other operations.

**Independent Test**: Delete a project, confirm it no longer appears in the list or search,
confirm its record is still stored and marked as deleted, and confirm that subsequently created
projects never receive its charge code.

**Acceptance Scenarios**:

1. **Given** an existing project, **When** the user chooses delete, **Then** a confirmation prompt
   shows the project's name and charge code and requires an explicit confirmation.
2. **Given** the delete confirmation, **When** the user cancels, **Then** nothing changes.
3. **Given** the delete confirmation, **When** the user confirms, **Then** the project is marked as
   deleted, a success confirmation is shown, and the project no longer appears in the list,
   search results, or detail view.
4. **Given** a deleted project, **When** a new project is created, **Then** the new project never
   receives the deleted project's charge code.
5. **Given** a project that has already been deleted (e.g., by another user), **When** the user
   tries to edit or delete it, **Then** a "project not found" message is shown and no change is
   made.
6. **Given** a deleted project, **When** the user looks for a way to restore or permanently remove
   it, **Then** no such action is offered in this feature.

### Edge Cases

- Project name made only of spaces is treated as empty; leading and trailing spaces are removed
  before saving and before checking uniqueness. The same applies to Client Name.
- Two users create or rename projects to the same name (ignoring case) at the same moment: only
  one succeeds; the other receives the "name already exists" message.
- A project is deleted, then a new project is created with the same name: allowed, and the two
  projects have different charge codes.
- Start or end date that is not a real calendar date (e.g., 31 February) is rejected.
- End date equal to the start date is accepted (a one-day project).
- Start date of today is accepted; start date of yesterday is rejected. "Today" is the current
  calendar date in the organization's business time zone.
- A user moves the Start Date of an existing project later than its current End Date: the save is
  rejected unless the End Date is also extended to on or after the new Start Date.
- Two users extend the End Date of the same project at the same time: the concurrent-edit rule
  (FR-020) applies; the second save is rejected and must be re-applied against the latest End Date.
- A user opens the create form before midnight and saves after midnight with the previous day as
  start date: the save is rejected because the start date is now in the past.
- The system cannot generate a unique charge code: creation fails with a clear message and no
  partial project is saved.
- Two projects are created at the same moment: each receives a different charge code.
- A charge code starting with zero (e.g., `00412345`) is searched for: it is found when searching
  by `00412345` or `0041`, and is always shown with all 8 digits.
- The user tries to set a charge code through any means other than the system (e.g., by
  submitting it with the form): the request is rejected and the value is never stored.
- An invalid project type or billing type (a value other than the allowed options) is submitted:
  it is rejected with a validation message.
- A Project Manager Name longer than 100 characters is submitted: it is rejected with a message
  stating the 100-character limit.
- The service becomes unavailable during save: the user sees an error, the entered data stays in
  the form, and the user can try again.
- A project is deleted while another user is editing it: the editor's save is rejected with a
  "project not found" message.
- A very large number of projects exists: the list remains usable through paging and search.

## Requirements *(mandatory)*

### Functional Requirements

#### Project creation

- **FR-001**: Users MUST be able to create a project by providing Project Name, Project Manager
  (name and email, see FR-023), Start Date, End Date, Project Type, Billing Type, and — for Client
  Projects — Client Name (see FR-003a).
- **FR-002**: Project Name, Project Manager Name, Project Manager Email, Start Date, End Date,
  Project Type, and Billing Type MUST all be required. Client Name is conditionally required
  (FR-003a).
- **FR-003**: Project Type MUST be exactly one of: Internal Project, Client Project.
- **FR-003a**: Client Name is free text. It MUST be provided (not blank after trimming, at most 100
  characters) when Project Type is Client Project. It MUST NOT be stored for Internal Projects;
  changing a project from Client Project to Internal Project MUST remove its Client Name. Client
  Name is not required to be unique.
- **FR-004**: Billing Type MUST be exactly one of: Billable, Non-Billable.
- **FR-005**: The system MUST NOT restrict which Project Type can be paired with which Billing
  Type; any combination is allowed unless a future business rule says otherwise.
- **FR-006**: Start Date and End Date MUST be valid calendar dates, and End Date MUST be on or after
  Start Date.
- **FR-006a**: When a project is created, Start Date MUST NOT be earlier than today. When a project
  is edited, a changed Start Date MUST NOT be earlier than today; an unchanged Start Date that has
  since passed MUST NOT block saving other changes.
- **FR-006b**: When a project is edited, the End Date MUST NOT be earlier than the End Date
  currently saved for that project (End Dates may be kept or extended, never shortened), and MUST
  still be on or after the Start Date.
- **FR-007**: Project Name MUST NOT be blank after leading and trailing spaces are removed, and MUST
  NOT exceed 100 characters. Whether names must be unique is set by FR-008.
- **FR-008**: Project Name MUST be unique among non-deleted projects. Uniqueness MUST be checked
  ignoring letter case and after removing leading and trailing spaces. Names of deleted projects
  MUST NOT block reuse. This rule MUST hold even when projects are created or renamed
  simultaneously.
- **FR-009**: The system MUST prevent duplicate project creation caused by repeated submission of
  the same create request (e.g., double-click or retry after a timeout).

#### Charge code

- **FR-010**: The system MUST automatically generate a Charge Code when a project is created.
- **FR-011**: A Charge Code MUST consist of exactly 8 numeric digits (0–9). Any 8-digit value,
  including those starting with zero (e.g., `00412345`), is valid. Leading zeros MUST be preserved
  everywhere the charge code is stored, displayed, searched, or returned.
- **FR-012**: A Charge Code MUST be unique across all projects, including deleted projects, and
  MUST NOT be reused once assigned.
- **FR-013**: Users MUST NOT be able to enter, supply, or change a Charge Code. Any charge code
  value supplied by a user MUST NOT be stored.
- **FR-014**: A project's Charge Code MUST be immutable: it MUST NOT change when the project is
  edited or deleted, for the entire life of the project.
- **FR-015**: If a unique Charge Code cannot be generated, the creation MUST fail with a clear
  message and no project MUST be saved.

#### Viewing and finding projects

- **FR-016**: Users MUST be able to view a list of non-deleted projects showing name, charge code,
  project manager name, start date, end date, project type, and billing type.
- **FR-017**: Users MUST be able to search projects by all or part of the project name, charge
  code, Project Manager name, Project Manager email, or Client Name, ignoring letter case, and to
  sort the list by name, charge code, start date, or end date.
- **FR-018**: The project list MUST be paged so that it remains usable with large numbers of
  projects.
- **FR-019**: Users MUST be able to open a detail view showing all fields of a single project,
  including Project Manager Name and Email, and Client Name for Client Projects.

#### Editing projects

- **FR-020**: Users MUST be able to edit all project fields except Charge Code. Edits MUST pass the
  same validation rules as creation (FR-002 to FR-008). If two users edit the same project at the
  same time, the later save MUST be rejected rather than silently overwriting the earlier one, and
  the user MUST be told to reload the latest version.

#### Deleting projects

- **FR-021**: Users MUST be able to delete a project after an explicit confirmation. Deletion MUST
  be a soft deletion: the project is excluded from the list, search, detail view, and editing, but
  its data and charge code are kept.
- **FR-022**: Deleted projects MUST be kept indefinitely. This feature MUST NOT provide restore or
  permanent purge of deleted projects; both are deferred to future features. The delete action
  MUST NOT permanently erase a project.

#### Project Manager

- **FR-023**: Each project MUST have exactly one Project Manager, recorded as a Project Manager
  Name and a Project Manager Email. Both are required. The name MUST NOT be blank after trimming
  and MUST NOT exceed 100 characters; the email MUST be a valid email address format. The same
  person MAY manage multiple projects.
- **FR-024**: The Project Manager Email MUST serve as the identifier used to link the project to a
  real user once a user/identity system is introduced, without losing existing project data.

#### Feedback, errors, and data quality

- **FR-025**: The system MUST validate all input on the server, independently of any checks in the
  user interface.
- **FR-026**: Validation failures MUST identify each failing field with a specific, readable message
  and keep the user's entered values.
- **FR-027**: Successful create, edit, and delete actions MUST show a clear success confirmation.
- **FR-028**: Error messages MUST NOT reveal internal technical details (e.g., error traces, query
  text, internal identifiers).
- **FR-029**: Each project MUST record when it was created and when it was last modified.
- **FR-030**: A detailed audit trail of project changes (who changed what, previous and new values)
  is deferred to a later feature. This feature MUST NOT prevent such a trail from being added
  later.
- **FR-036**: This feature is designated **development-only** under the Constitution's Principle III
  exemption. It MAY be deployed to lower (non-production) environments such as development and
  test, and MUST NOT be deployed to production until authentication and authorization are
  implemented for it.

#### User experience

- **FR-031**: The Project Management area MUST provide clear navigation between the project list,
  project detail, create, and edit views, with consistent page titles and actions.
- **FR-032**: Create and edit forms MUST group related fields logically (e.g., general information,
  schedule, classification) and clearly mark required fields.
- **FR-033**: Every view that loads data MUST show a loading state, an empty state where
  applicable, and an error state with a retry option.
- **FR-034**: All Project Management views MUST meet WCAG 2.1 Level AA, including full keyboard
  operation, visible focus, labelled form fields, errors announced to assistive technology, and
  sufficient color contrast.
- **FR-035**: The visual design MUST give a structured enterprise business-application feel
  (clear hierarchy, consistent layouts, data tables, organized forms) without copying any third
  party's branding, proprietary visual design, or assets. Compliance is verified by design review
  against the screen and layout rules agreed during planning.

### Key Entities *(include if feature involves data)*

- **Project**: A unit of work that time may later be recorded against. Attributes: Project Name,
  Project Manager (name and email), Start Date, End Date, Project Type, Client Name (Client
  Projects only), Billing Type, Charge Code, created and
  last-modified timestamps, and deletion status (with deletion timestamp).
- **Charge Code**: An 8-digit numeric identifier assigned once by the system to a single project.
  It is unique among all projects (active and deleted), unchangeable, and never reused.
- **Project Manager**: The person responsible for a project, captured as a name and work email
  (FR-023). The email is the future link to a user in an identity system. In this feature it is
  stored as part of the project, not as a separately managed record.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user can create a valid project and see its generated charge code in under 2
  minutes.
- **SC-002**: 100% of created projects have a charge code of exactly 8 numeric digits, and no two
  projects (active or deleted) ever share a charge code, including when projects are created at the
  same time.
- **SC-003**: 100% of invalid submissions covered by the validation rules are rejected with a
  field-specific message, and no invalid project is ever saved.
- **SC-004**: With at least 10,000 projects, users find a project by any searchable field (FR-017)
  and see results within 2 seconds in 95% of searches.
- **SC-005**: 0 projects are permanently erased by the delete action; every deleted project's data
  and charge code remain stored and its charge code is never reassigned.
- **SC-006**: 0 lost updates: when two users edit the same project at the same time, the earlier
  saved change is never silently overwritten.
- **SC-007**: All Project Management views pass a WCAG 2.1 AA review with 0 critical or serious
  issues, and every task in this feature can be completed using only a keyboard.
- **SC-008**: At least 90% of first-time users complete create, find, edit, and delete tasks
  without help in usability testing.

## Assumptions

- Any person who can reach a lower environment where the application is deployed can create,
  view, edit, and delete projects, because authentication and authorization are out of scope for
  this development-only feature (FR-036).
- Mandatory fields are as defined in FR-002 and FR-003a. Open-ended projects with no End Date are
  not supported in this feature.
- Start Date cannot be in the past (FR-006a). "Today" is determined by the organization's business
  time zone, which is a single, configurable value for the whole application.
- Project Name is limited to 100 characters; no other restrictions on characters are applied.
- Client Name uses the same 100-character limit as Project Name. It is free text, not a link to a
  managed client record.
- Dates are calendar dates without a time of day.
- There is no project status (e.g., active, completed) beyond deleted / not deleted; a status
  derived from dates is out of scope.
- No restrictions on deleting a project are applied in this feature, because no time entries or
  other dependent records exist yet. Future features that reference projects may add rules.
- The application is used in English only; localization is out of scope.
- Project Manager Email is checked for valid format only. It is not verified against a directory,
  its domain is not restricted, and it is stored and compared ignoring letter case.
- Updating a person's name or email across all their projects at once is out of scope; each
  project is edited individually.

### Out of Scope

- Login, logout, user accounts, identity provider integration, tokens, roles, and permissions
  (deferred to a later feature).
- Audit trail of project changes (who changed what and when, with previous and new values)
  (deferred to a later feature).
- Timesheets, time entries, approvals, reporting, and clients/customers as managed entities
  (Client Name is free text only).
- Bulk import/export of projects.
- Changing or regenerating a charge code.
- Restoring deleted projects, viewing a list of deleted projects, and permanently purging projects.

### Dependencies

- **Future identity system**: Needed to link the Project Manager to a real user (FR-024) and to
  enforce authentication and authorization.
- **Future audit feature**: Needed to track project changes and the acting user (FR-030).

### Constitution Alignment

Alignment with `.specify/memory/constitution.md` v1.3.0. No unresolved conflicts remain; the two
deferrals below use explicit constitutional provisions and MUST be recorded in the plan:

- **Principle III (Security by Design, NON-NEGOTIABLE)** requires authentication and server-side
  role-based access control. This feature uses the Principle III **development-only exemption**:
  it is designated development-only (FR-036), the identity architecture does not yet exist, and
  the design MUST allow authentication and authorization to be added later without rewriting
  business logic. The plan MUST record the exemption in Complexity Tracking and describe how
  production deployment is prevented. All other Principle III rules (input validation,
  parameterized queries, secret handling, HTTP security controls) still apply.
- **Principle VI (Auditability)** requires an audit trail and the acting user. This feature uses
  the Principle VI **pre-identity audit deferral**: the audit trail is deferred (FR-030), created
  and last-modified timestamps are kept (FR-029), deleted projects are never erased (FR-022), and
  the audit trail can be added later without changing existing data.
- **Principle V (Data Integrity & Lifecycle)** is satisfied: soft deletion is used, and restore
  and purge are explicitly excluded from this feature (FR-021, FR-022).
- **Personal data**: Project Manager Email is personal data. It MUST NOT appear in logs beyond what
  is needed for diagnosis (Principle VII).
